## THE FIVE-HOUR HANG — read before running anything with `--discography`

The first `--discography --write` run printed its three startup lines and then did nothing
for **5h12m**. Measured, not guessed: zero CPU delta over 60 seconds, zero open sockets
across 12 samples. It was asleep, not slow.

Cause, at what was then `scripts/backfill-genres.mjs:1112`:

```js
const retryAfterSeconds = Number(res.headers.get('Retry-After')) || 1;
await delay(retryAfterSeconds * 1000);
```

**Spotify hands a client-credentials app that has exhausted its quota a `Retry-After`
measured in hours** (we have since seen 63,762s ≈ 17.7h). The code honoured it literally.
My briefing said "honour Retry-After" and never specified a ceiling — the agent implemented
exactly what was asked.

Nothing was lost: the script writes `roster.json` only at the very end, so the hang cost
five hours and no data.

Fixed in `0592a8c`: ceiling of 60s, anything larger aborts immediately naming the value;
every 429 logged as it arrives; three consecutive 429s abort the run; every request carries
a 30s `AbortSignal.timeout` so a half-open socket cannot hang the walk by the other route.

**The deeper lesson is that the hang was invisible.** Progress logging existed only as a
nice-to-have for the *next* chunk; it is what would have caught this in minute two. Never
run a multi-hour walk without it again.

## Why the discography match is worth waiting for

Prototyped against the live APIs on 8 of the hardest cases (3+ competing candidates).
**Resolved 8/8**, and the separation is not subtle: the correct artist shares 9–29 normalised
release titles with our roster artist, every impostor shares 0–2.

The method: pin our artist on Spotify by matching the `avatarUrl` the roster already stores
(it is a Spotify CDN image, so an exact URL match is proof of identity, not a name guess),
pull their release titles, then pull each iTunes candidate's and score the overlap.

**"Tash" resolved to Contemporary R&B, not Hip-Hop/Rap** — 24 of its 28 iTunes candidates are
hip-hop and Apple ranks a hip-hop Tash first, so "pick the most popular / first result" would
have written the wrong genre. This is the concrete reason the cheap heuristic was rejected.

Two rules that are not optional:
- **A margin rule.** The James Newman audiobook genuinely shares a release titled *Therapy*
  with the musician, so ">0 overlap wins" is unsafe. Winner needs ≥2 overlap (avatar pin) or
  ≥5 (name pin), AND ≥3× the runner-up.
- **`avatarUrl` pins are stronger than name pins.** A namesake's discography can match a wrong
  iTunes candidate *coherently* — the worst failure mode available. Hence the higher bar for
  name pins, and `pinMethod` recorded on every fill so they stay auditable.

## Process notes worth keeping

1. **I gave three low time estimates this session** (30–35 min for a chunk that was hung;
   ~2h then ~1.6h for a walk that never ran). The pattern is costing the dominant call and
   forgetting its companions — I counted iTunes calls and forgot each artist also makes
   several Spotify ones, each batched lookup takes its own full `--delay`, and so on. The fix
   shipped in `c82cda5`: the run now measures and reports its own rate. Quote that, don't
   predict.
2. **I declared the Spotify quota recovered after testing one endpoint.** The one that was
   broken was a different one. Test the endpoint you actually depend on.
3. The user's instinct to check images was right in substance — matching the *person* rather
   than ranking by popularity — even though the literal version (compare portraits) is
   impossible, since iTunes returns no artist image. Discography overlap is the same idea in a
   form the APIs actually support. Worth remembering that a suggestion can be correct in
   intent and wrong in mechanism.
4. Killing a hung run cost nothing because the script writes once, at the end. That design
   keeps paying off — preserve it.
