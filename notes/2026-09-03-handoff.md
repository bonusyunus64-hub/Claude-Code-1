## 1. THE `{{artistSummary}}` WARNING WAS THE LINTER'S BUG. Commit `edc6884`, pushed

The user saw, in the Shared-Manager panel:

> Unrecognized template variable `{{artistSummary}}` — this app only ever fills in
> `{{managerName}}`, `{{artistName}}`, ... Anything else is never replaced and mails out to the
> recipient as this exact literal text.

**It renders fine.** `buildMultiArtistMessage` (`lib/demosSend.ts:145`) and the preview mirror
(`app/dashboard/previewEntries.ts:204`) both fill it. `computeSpamScore` had a single hardcoded
`KNOWN_TEMPLATE_VARS` set of nine names, written before the shared-manager feature existed and
never updated. So the app flagged **its own `DEFAULT_MULTI_ARTIST_TEMPLATE`** with its
highest-severity check, on a claim that was false.

Five names were missing: `artistSummary`, `artistNames`, `artistCount`, `otherCount`,
`allArtistNames`.

**Fixed per-panel, not globally, and that distinction is the whole design.** `computeSpamScore`
now takes the fillable set as an optional second parameter (`DEFAULT_TEMPLATE_VARS`, unchanged
nine names); `MultiArtistTemplatePanel` passes `MULTI_ARTIST_TEMPLATE_VARS`. Merging the five
into one global set would have been three lines and **would have introduced a worse bug than it
fixed**: the single-artist paths (`buildEmailsForArtist`, the custom-contacts branch,
`broadcastSend`, `autoFollowUp`) never populate them, so `{{artistSummary}}` typed into the main
pitch template would have passed silently and mailed out as literal braces — a false negative on
the loudest check in the file, traded for a false positive on one panel. **There is a test
asserting that exact direction; do not "simplify" it away.**

Also added the `{{allArtistNames}}` chip — fillable all along, never advertised.
`{{artistName}}` and `{{pronoun}}` stay deliberately unadvertised per the 08-22 note, while
still not being flagged.

tsc clean, **1094 tests** (was 1081), build clean.

## 2. BACKFILL HARDENED AFTER A 502 ATE A CHUNK. Commit `79aab5d`, pushed

**The first run tonight crashed and lost 19 completed fills.** Not a quota abort — Spotify
returned a transient **502 Bad Gateway** on `/search` at artist 20 of 212, and the throw went
straight past the 08-26 abort branch. `roster.json` untouched, all 19 discarded.

Root cause was narrower than "the abort fix is incomplete": **`fetchSpotify`'s retry loop
retried dropped sockets and 429s and nothing else.** Any other non-OK status fell through to an
immediate `throw`, so a 502 got exactly one attempt despite being the same transient
backpressure as a dropped connection.

Two parts, because the retry alone is not enough:

1. **500/502/503/504/408 now retry** on the existing bounded backoff
   (`SPOTIFY_RETRYABLE_STATUSES`). Other 4xx still throw unretried — deterministic, and retrying
   them only burns quota. **iTunes' `fetchWithRetry` had the identical gap** (403/429 retryable,
   5xx not) and got the same fix; it has no unit coverage, flagged in its own comment.
   `discography-match.mjs` needed nothing — it never calls `fetch` directly, everything goes
   through injected deps.
2. **The walk saves completed fills on ANY unexpected error**, not only
   `SpotifyQuotaExhaustedError`. Nothing is swallowed: `main()` prints the full stack, the run is
   logged `aborted: true`, the banner is loud, exit is still 1. New `abortKind`
   (`'quota' | 'unexpected'`) drives the banner wording — "come back tomorrow" is wrong for a
   bug. New `abortError` carries the raw Error for the stack only and **never reaches the JSON
   log**; `abortReason` remains the serialised string.

**A pre-existing test was rewritten, deliberately.** `scripts/backfill-genres.test.mjs`'s "lets a
non-quota error propagate out of backfillGenres uncaught, exactly as before" asserted
`.rejects.toBe(boom)` — it encoded the old decision rather than guarding the 08-26 fix, and its
own fixture error was `'unexpected Spotify 500'`, the very case that cost 19 fills. Inverted,
with the incident recorded in the test body.

tsc clean, **1102 tests** (was 1094).
