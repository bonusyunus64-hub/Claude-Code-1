## 1. THE WRITE-ON-ABORT FIX — DONE, commit `9e1f4b9`, pushed

The fix the 08-26 note specified is in. `backfillGenres` now catches
`SpotifyQuotaExhaustedError` itself, stops its walk, and returns its ordinary
`{ artists, stats, log }` shape with `aborted` / `abortReason` attached, so `main()` takes its
**normal** summary-and-write path. Every requirement from the 08-26 spec is met:

- the aborting artist and every un-attempted artist pass through as their **untouched original
  object** — never logged as skipped (a `PERMANENT_SKIP_REASONS` entry would have excluded them
  from all future runs), never counted as attempted, fully eligible next run;
- any non-quota error still propagates with its full stack and still writes nothing;
- an aborted run exits **non-zero**, in dry-run mode too;
- the `runs` entry in the provenance log is marked `aborted`;
- the summary ends in a banner that can't be skimmed past.

**Design decision (`stats.attempted`):** the aborting artist's `attempted` increment is rolled
back. In every other path `attempted == filled + sum(skipped.*)` — one attempt, one verdict.
The aborting artist produced no verdict, so counting it would make the summary imply a skip or
fill that doesn't exist. Console summary and the log's `runMeta.stats` both read from the same
`stats` object, so they can't disagree.

**Verification (re-run by me, not taken on trust):** `backfill-genres.test.mjs` 94 passed ·
full suite 1080 passed across 45 files · `tsc --noEmit` clean · `eslint` clean. Five new tests
cover the abort. Nothing was ever run against live APIs, so today's quota is untouched.

## STILL OPEN

- ~~Cutting Spotify calls per artist in the discography path~~ — **investigated 2026-08-27 and
  deliberately parked. Don't re-attempt it without new information; the reason is arithmetic,
  not implementation quality.**

  The hoped-for cut was: fetch Spotify album page 1, and skip page 2 when page 1 already settles
  the verdict (3 calls/artist → 2, i.e. ~75/day instead of ~56). **It can almost never be proved
  safe.** The acceptance rule needs the winner to beat every rival by 3x. Page-1 overlap caps at
  10, and a rival's worst case after a hypothetical page 2 is `overlap + min(10, ownCatalog −
  overlap)`. So the moment ANY competing candidate has a catalogue of 4+ releases,
  `3 x 4 = 12 > 10` makes the margin structurally unprovable from page 1 and page 2 must be
  fetched anyway. Only ~15-28% of two-page cases could ever skip it.

  Measured from the log: 35 discography-resolved fills (28 avatar-pinned, 7 name-pinned), 29 of
  which genuinely fetched page 2. Real gain ≈ 5-7% fewer calls ≈ **+3-4 artists/day**, i.e. about
  0.3 days off the 5-day priority grind.

  Parked because that gain didn't justify: a ~190-line restructure of the module that decides
  `discographyInconclusive` (a PERMANENT skip reason); a documented side effect where a skipped
  page 2 makes the logged `overlap`/`ourReleaseCount` page-1-only lower bounds — degrading the
  exact provenance data the worklist rebuild depends on; and stacking a second unrelated change
  into the same night as the abort fix's first live run.

  A working, tested implementation existed (31 tests passing, full suite green) and was reverted
  out of the working tree — **deliberately, because leaving it there meant tonight's real run
  would have executed unshipped code.** The patch was saved to that session's scratchpad, which
  is ephemeral; regenerating it is cheap if the trade ever changes. What's worth keeping is the
