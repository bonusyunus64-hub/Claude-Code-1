## THE MULTI-ARTIST PITCH — what changed and why

**The old behaviour:** `dedupeByRecipient` kept the highest-`rank` message per address and
`lib/demosSend.ts` set `rank: artist.spotifyFollowers`, so a manager repping several matched
artists got pitched their **biggest** artist and the rest were silently dropped.

**The user's redirect, which was the right call.** I was about to ask which single artist
should win. He asked instead: why pick at all — why not a different email that names several,
on the premise that the manager's taste across those acts is the reason for the pitch. That
is what shipped.

**Measured before building** (do not re-derive, the numbers are here):

| | |
|---|---|
| Manager inboxes repping 2+ artists, roster-wide | 2,173 of 4,220 (51.5%) |
| Artists sitting behind a shared inbox | 5,795 of 7,230 |
| Biggest single inbox | 32 artists |
| **In a realistic campaign** (Pop / Alternative / Dance / Country, matchMode any) | **20–39% of inboxes rep 2+** |
| Largest in-campaign group | 8–13 artists |

For a Dance/Edm pitch, 1,029 matched artists used to collapse into 856 emails naming 856 of
them. That gap is what this closes.

### The decisions, and who made them

- **Name up to 3, count the rest** (`NAMED_ARTIST_CAP`). User's choice.
- **Order by genre fit, then followers.** User took the recommendation.
- **Warn above 3, don't block.** User's explicit choice — he wants to narrow the filters and
  avoid truncation entirely, with the "and N others" copy as the safety net rather than the
  plan. Do not turn this into a confirm step or an auto-trim.
- **Follow-ups reuse the existing follow-up template.** User took the recommendation.
- **No A/B subject test on the multi-artist email** — my call, flagged to him, not vetoed.
  Splitting an already-smaller group makes the test unreadable and it'd mean a fourth subject
  box.
- **No saved-template library on the new panel** — my call. Add one if a real need shows up.

### Things that will look like bugs and are not

- **`{{pronoun}}` renders a flat `'they'`** in the multi-artist email. The email is about
  several people; resolving it from the lead artist would be wrong about the others.
- **`{{artistName}}` and `{{pronoun}}` are deliberately absent from the panel's variable
  chips** but still render if typed. `artistName` resolves to the lead artist only, which
  invites copy that names one artist in an email whose premise is that it names several.
- **The overflow count is resolved in the data, not the template.** `renderTemplate` has no
  conditionals, so `{{otherCount}}` in the default copy would read "and 0 others" when
  nothing was truncated. `buildArtistNameVars` produces `{{artistSummary}}` already correct
  in every case — including the **singular "and 1 other"**.
- **A request with no `multiArtistTemplate` behaves exactly as it did before this feature.**
  That is load-bearing: it stops a stale browser tab sending copy the user has never read,
  and it is also the entire mechanism by which follow-ups stay on single-artist copy — the
  client omits the field, so the server needs no "is this a follow-up" flag.

### Two bugs caught in review — both the same class

Both were the preview or the warning **re-deriving a per-row decision from the address**
instead of from the candidate that actually survived deduplication.

1. **Preview modal (caught before commit).** A hand-added custom contact sharing an address
   with a manager repping 2+ matched artists was rendered through the multi-artist template
   using its own vars, leaking literal `{{artistNames}}` into the previewed subject and body.
   Proven with a throwaway test, then fixed by excluding custom-contact addresses when the
   multi-artist set is built — true by construction. Never reached the send path.
2. **Warning banner (same root cause, one round later).** Same missing exclusion, so the
   banner could warn about truncating an email that address was never going to receive.

**The invariant to hold on to:** a custom contact always wins its address, so that address
can never be a multi-artist row. Anywhere that decides "is this multi?" must respect that.
There is now a test asserting **no unrendered `{{` placeholder survives into a previewed
body** — that is the cheap net that would have caught #1 on its own.

### THE QUOTA IS THE BINDING CONSTRAINT, NOT THE RUNTIME — read before planning any walk

The 250 chunk **aborted after 19 artists** on a second 429: `Retry-After 81049s` (~22.5h,
clear ~18:00 on 2026-08-23). The abort was clean and nothing was written, so the 16 fills in
that chunk were lost — the write-once-at-the-end design behaving exactly as intended.

**The lesson that supersedes the 08-21 note's throughput planning:** wall-clock rate
(4.7 artists/min) is irrelevant. The real budget is **~59 artists per ~22.5h window** — that
is all the canary (40) plus this chunk (19) got through before the quota was exhausted again.

**`200 ok` on `/artists/{id}/albums` proves the endpoint is unblocked, not that there is
budget behind it.** That check passed at 17:47 and the quota was gone by ~19:00. There is no
known way to read remaining quota; treat every run as possibly the last one of the day.

**Do not "optimise the call volume" as a fix — it is already at the floor.** The 08-22 cut in
`scripts/discography-match.mjs` took it from ~6 calls/artist to ~2-3, and 2 is the structural
minimum (one pin + one albums page). 813 artists at this budget is **~14 days of daily
chunks**.

### What the remaining 851 are actually worth (measured, no API calls needed)

Of the 851 genre-less artists, **565 sit behind a manager inbox that some genre-tagged artist
already reaches** — filling their genre wins no new inbox. Only **286 are the sole route to
their manager**, covering **279 inboxes that no genre filter can currently reach** (6.6% of
4,220).

So the honest split is ~5 days of drip for all the reach, or ~14 for the last 565. The 565
are not worthless — now that the multi-artist pitch ships, a genre on one of them means it
gets **named** in the email to a manager who is already being reached. That is a real gain,
just a much smaller one than reach.

**This is a live decision for the user — see STILL OPEN.** The script has no
artist-targeting flag today (`--retry-reasons` filters by skip reason, not by artist), so
prioritising the 286 needs a small flag added first.

### Resume the walk — 2026-08-23, after ~18:00

**The user decided to spend the quota on the 286 first.** `--only-unreachable` (added this
session, `1e90f09`) is what targets them. THIS is the command now:

```
cd "C:\Music Distribution Platform"
node --env-file=.env.local scripts/backfill-genres.mjs --only-unreachable --discography --retry-reasons ambiguousName,unmappableGenre --limit 60 --delay 3000 --write
```

Note `--limit 60`, not 250 — sized to the measured ~59-artist daily budget so the run ends
near where the quota does. A bigger limit doesn't get more done; it just aborts later and
throws away that chunk's fills.

**The flag recomputes its set from the roster every run**, so it needs no maintenance as
fills land: once an artist gets a genre, anyone sharing their inbox stops qualifying. The
candidate pool intersected with `--retry-reasons` is **276** (the other 10 of the 286 sit
under `noNameMatch`/`noGenreOnRecord`/`discographyInconclusive`, deliberately excluded).

Dry-run any time at zero quota cost with `--limit 0` — it prints the qualifying counts and
performs no lookups at all.

After the 286 are done, drop `--only-unreachable` to work the remaining 565, or don't — that
was the point of the split.

Repeat until `Eligible` stops falling; filled artists stop being eligible, so each run picks
up where the last left off. The script writes once at the end, so a crash mid-chunk loses
that chunk and nothing else — chunk deliberately. Commit after each. Auto-push is authorised.

`noNameMatch` (28) and `noGenreOnRecord` (5) stay **deliberately excluded** on the user's
