## SPOTIFY IS DEAD AS A GENRE SOURCE — read before reaching for it again

As of 2026-08-17 the Spotify Web API returns artist objects **without** `genres`, `followers`,
or `popularity` for client-credentials apps. Not zero, not empty — the fields are absent from
the payload. Verified with a raw `GET /v1/artists/06HL4z0CvFAxyc27GXpf02` (Taylor Swift),
HTTP 200, body containing only `external_urls`, `href`, `id`, `images`, `name`, `type`, `uri`.
Credentials in `.env.local` are valid; identity lookups still work.

This is why the original script's first real run filled 0 of 50 and rejected 49 as
`followerMismatch`: Spotify sent no follower number, it defaulted to 0, and 0 is nowhere near
the roster's real counts. The safety check worked — it wrote nothing.

`lib/spotify.ts` is unaffected: it only ever used the artist URL, which is still returned.
No user-facing feature broke.

Note the script needs `node --env-file=.env.local` — it reads `process.env` and does not load
that file itself.

## The matching problem, and the rule that solves it

98% coverage is misleading alone: **37% of names return more than one distinct iTunes artist**,
and they usually disagree. 11 artists named "Harpy", 12 named "SOFY", 10 named "ian", 19 named
"Tash". A naive "first exact match wins" would have written "Rock" onto Harpy chosen from
eleven candidates. iTunes returns **no follower count**, so the old cross-check cannot be ported.

The rule now implemented — exactly one exact-name match, **or** several that all agree on genre:

- yields ~57% fill in practice (114 of the first 200)
- catches the dangerous cases: real production skips included "James Newman" (Pop / Fiction /
  Horror), "Will Jay" (Pop / Family Stories for Young Adults), "Peter Fenn" (Art & Architecture
  / Pop) — audiobooks and podcasts sharing a musician's name
- `Self-Development` and `Worldwide` showed up as unmappable genres, both from wrong matches

**Residual risk, accepted knowingly:** a unique name is not proof of the right artist. If our
artist isn't on iTunes but a different, uniquely-named one is, we write their genre. There is
no available cross-check. Blast radius is a mildly mis-targeted pitch, reversible via git —
unlike the wrong-email failure mode this project has been burned by.

### `data/genre-backfill-log.json` — the provenance record
Exists because iTunes gives **one broad genre** where ROSTR gives rich multi-value strings, so
backfilled artists surface under `Hip Hop & Rap` but never under `Underground Hip Hop`. The user
has a later plan for narrowing these; this log is what makes that possible.

- Per filled artist: name, rostrUrl, raw `primaryGenreName`, `mappedGenre`, matchType
  (`unique`/`unanimous`), matchCount, iTunes artistId + artistLinkUrl.
- Per skipped artist: name, rostrUrl, reason, and for `ambiguousName` the competing genres.
  **This half is the ready-made worklist** for the artists we couldn't resolve.
- **Merges across runs** (keyed by `rostrUrl`, current run wins, artists can move between
  filled/skipped without leaving a stale duplicate). `runs` is an appendable history.
- Refuses to write — loudly, before touching anything — if an existing log is corrupt or
  misshapen, rather than silently starting fresh and losing accumulated provenance.
- Contains **no manager emails or names**; verified by regex. Safe to commit, and committed.
- `overLimit` artists get a counter but no log entry (they were 296KB of a 296KB file).
